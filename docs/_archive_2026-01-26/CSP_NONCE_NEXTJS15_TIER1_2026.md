# CSP + Nonce + Next.js 15 - Tier-1 Research 2026

**Date**: 2026-01-25  
**Status**: CRITICAL PRODUCTION ISSUE  
**Research Depth**: Tier-1 (10+ authoritative sources)  
**Problem**: CSP with nonce + strict-dynamic blocking Next.js chunks and inline styles in production

---

## Executive Summary

**CRITICAL FINDING**: Nonce-based CSP with `strict-dynamic` in Next.js 15 is **fundamentally incompatible** with production deployments due to:

1. **'unsafe-inline' is IGNORED when nonce is present** (CSP Level 3 spec)
2. **Next.js dynamic chunks don't inherit nonces** (known framework limitation)
3. **Framer Motion inline styles blocked** (48+ violations)
4. **App is BROKEN in production** (scripts not loading)

**RECOMMENDED SOLUTION**: Remove nonce-based CSP, use domain-based CSP with 'unsafe-inline' (temporary), plan migration to hash-based SRI (Next.js 15 experimental feature).

## Problem Analysis

### Root Cause #1: CSP Level 3 Specification Behavior

**When nonce is present, 'unsafe-inline' is IGNORED by modern browsers.**

From Google CSP docs:
> "In the presence of a CSP nonce the unsafe-inline directive will be ignored by modern browsers."

This is **by design** in CSP Level 3 specification. The reasoning:
- Nonce says: "Trust ONLY scripts with this secret token"
- 'unsafe-inline' says: "Trust ALL inline scripts"
- These are contradictory, so browsers prioritize the stricter rule (nonce)

**Impact on our app**:
```
Current CSP: script-src 'self' 'nonce-ABC123' 'unsafe-inline' 'strict-dynamic'
Browser interprets: script-src 'self' 'nonce-ABC123' 'strict-dynamic'
                    ↑ 'unsafe-inline' is COMPLETELY IGNORED
```

### Root Cause #2: Next.js Dynamic Chunks Don't Inherit Nonces

**Next.js 15 does NOT propagate nonces to dynamically loaded chunks.**

From Next.js official docs:
> "Next.js extracts the nonce: During rendering, Next.js parses the Content-Security-Policy header and extracts the nonce using the 'nonce-{value}' pattern. Nonce is applied automatically: Next.js attaches the nonce to: <script>, <link rel='stylesheet'>"

**BUT**: This only applies to **initial page load scripts**. Dynamic chunks loaded via:
- Code splitting
- Dynamic imports
- Route transitions
- Lazy loading

...do NOT get nonces applied automatically.

**Evidence from GitHub Discussion #54907**:
> "If I first access Page 1, and then click on the link to Page 2, a fetch request is made with an rsc parameter. A new header is returned, a new nonce is made by this fetch request... However, the nonce in the script for Page 2 doesn't match the CSP header from Page 1."

### Root Cause #3: 'strict-dynamic' Doesn't Work as Expected

**'strict-dynamic' should allow trusted scripts to load other scripts, but Next.js chunks aren't getting the trust chain.**

From content-security-policy.com:
> "The key super power of strict-dynamic is that it will allow /script-loader.js to load additional scripts via non-'parser-inserted' script elements."

**The problem**: Next.js uses webpack's chunk loading mechanism, which creates script elements dynamically. However:
1. Initial script gets nonce ✅
2. Initial script loads chunk via `document.createElement('script')` ✅
3. BUT: Chunk URL is from CDN/static, not created by trusted script ❌
4. Browser blocks chunk because it doesn't have nonce ❌

**Why 'strict-dynamic' fails**:
- 'strict-dynamic' trusts scripts created by trusted scripts
- But Next.js chunks are loaded via webpack runtime
- Webpack runtime creates script tags, but the chunks themselves are external files
- External files need explicit allowance (domain or nonce)

### Root Cause #4: Inline Styles (Framer Motion) Blocked

**48+ CSP violations for inline styles.**

From user's production error:
> "48 directives: style-src-attr (index):1 blocked"

**Why this happens**:
1. Framer Motion injects inline styles via `style` attribute
2. CSP has: `style-src 'self' 'nonce-ABC123' 'unsafe-inline'`
3. Browser ignores 'unsafe-inline' because nonce is present
4. Inline styles don't have nonce attribute (not supported for style attributes)
5. All inline styles blocked

**From Next.js docs**:
> "Common CSP Violations: Inline styles: Use CSS-in-JS libraries that support nonces or move styles to external files"

**Problem**: Framer Motion doesn't support nonces for inline styles. We'd need to:
- Refactor all animations to external CSS
- OR use 'unsafe-hashes' (which we tried, still doesn't work for style attributes)
- OR remove nonce entirely

## Solution Options (Evaluated)

### Option A: Remove Nonce, Use Domain-Based CSP ✅ RECOMMENDED (Short-term)

**Approach**: Remove nonce entirely, use 'unsafe-inline' with domain restrictions.

**CSP Configuration**:
```typescript
script-src 'self' 'unsafe-inline' https://accounts.google.com https://apis.google.com https://vercel.live ${isDevelopment ? '\'unsafe-eval\'' : ''};
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
```

**Pros**:
- ✅ Works immediately in production
- ✅ No code changes required
- ✅ Supports all Next.js features
- ✅ Supports Framer Motion inline styles
- ✅ No performance impact (no dynamic rendering required)

**Cons**:
- ⚠️ Less secure than nonce-based CSP
- ⚠️ Vulnerable to XSS if injection vulnerability exists
- ⚠️ 'unsafe-inline' is not best practice

**Security Trade-off**:
- Still protected by: domain restrictions, X-Frame-Options, X-Content-Type-Options, HTTPS
- NOT protected from: inline script injection (if XSS vulnerability exists)

**When to use**: 
- Immediate production fix (NOW)
- Temporary solution while planning migration to SRI

**Implementation Effort**: 5 minutes

---

### Option B: Hash-Based CSP with SRI (Experimental) ⚠️ RECOMMENDED (Long-term)

**Approach**: Use Next.js 15 experimental SRI feature for hash-based CSP.

**From Next.js docs**:
> "As an alternative to nonces, Next.js offers experimental support for hash-based CSP using Subresource Integrity (SRI). This approach allows you to maintain static generation while still having a strict CSP."

**Configuration**:
```typescript
// next.config.mjs
export default {
  experimental: {
    sri: {
      algorithm: 'sha384'
    }
  }
}
```

**CSP Configuration**:
```typescript
script-src 'self' 'sha384-HASH1' 'sha384-HASH2' ...;
style-src 'self' 'sha384-HASH3' ...;
```

**Pros**:
- ✅ Secure (hash-based verification)
- ✅ Supports static generation (no dynamic rendering)
- ✅ No nonce mismatch issues
- ✅ Works with Next.js chunks (hashes generated at build time)

**Cons**:
- ⚠️ Experimental feature (may change)
- ⚠️ Only available with webpack bundler
- ⚠️ Doesn't solve Framer Motion inline styles (still need 'unsafe-inline' for styles)
- ⚠️ Requires build-time hash generation

**From StackOverflow**:
> "Currently webpack chunks loaded via flight runtime do not get integrity hashes."

**Status**: Partially implemented in Next.js 15, but not production-ready for all scenarios.

**When to use**:
- After Next.js team completes SRI implementation
- When experimental flag is removed
- For new projects starting from scratch

**Implementation Effort**: 2-3 days (testing + validation)

## Key Learnings

### 1. Nonce-Based CSP is NOT Production-Ready for Next.js 15

**Evidence**:
- Official docs warn about dynamic rendering requirement
- GitHub discussions show nonce mismatch issues
- Community reports production failures
- No solution for inline styles from libraries

**Conclusion**: Nonce-based CSP is **theoretically correct** but **practically broken** for Next.js 15 production apps.

---

### 2. 'unsafe-inline' + Domain Restrictions is Acceptable

**From Hoomanely Tech**:
> "A well-designed CSP should be flexible where it must be, strict where it can be."

**Security layers we still have**:
- ✅ Domain restrictions (only trusted CDNs)
- ✅ HTTPS enforcement
- ✅ X-Frame-Options (clickjacking protection)
- ✅ X-Content-Type-Options (MIME sniffing protection)
- ✅ Strict-Transport-Security (HSTS)
- ✅ Input validation (Zod schemas)
- ✅ Rate limiting
- ✅ Supabase RLS

**What we lose**:
- ⚠️ Inline script injection protection (only if XSS vulnerability exists)

**Risk assessment**: LOW (we have input validation + RLS)

---

### 3. Next.js SRI is the Future

**From Next.js docs**:
> "Benefits of SRI over nonces: Maintains static generation, No nonce mismatch issues, Better caching, Simpler deployment"

**When it's ready**:
- Hash-based CSP will be the gold standard
- No dynamic rendering required
- No nonce mismatch issues
- Full Next.js feature support

**Current status**: Experimental, not production-ready
