10) Percorso verso setup reali (prop/challenge)

10.0 Venue Selection: scegliere dove cercare setup

Layer che decide quale arena oggi ha la migliore combinazione opportunita / rischio / costi e quali mercati sono vietati (regole, costi, eventi, liquidita).

Input minimi

  • ChallengeSpec (vincoli per arena)
  • cost_features per arena (spread/slippage proxy + quantili)
  • Regime/Context per arena (trend/expansion + volatility)
  • Catalyst (eventi specifici asset)

OpportunityScore (proxy-based)

OpportunityScore = Trend/Expansion + Catalyst + Liquidity − CostRisk − EventRiskPenalty

Prima gate, poi score: se venue_gate=DISABLED o data_quality<min → score = -INF.

Componenti discretizzati via quantili robusti per arena: Liquidity ∈ {0,0.5,1} da p33/p66 volume/range; CostRisk ∈ {0,0.5,1} da p33/p66 spread/slippage proxy; Trend/Expansion ∈ {0,0.5,1} da classificatore regime; Catalyst ∈ {0,1}; EventRiskPenalty ∈ {0,1}.

Output contract

  • venue_gate: {CRYPTO, FOREX, FUTURES, EQUITIES_NEWS} → ENABLED/DISABLED
  • primary_arena_today
  • secondary_arena (opzionale)
  • watchlist_target (es. ["TSLA"])
  • fallback_index (es. ["NQ"])
  • catalyst_strength: LOW/MED/HIGH
  • universe_today: { arena: [symbols...] }
  • why (motivazione auditabile)

Regole dure (anti-errore)

  • Follow the energy: se un’arena ha expansion + liquidita ok + costi accettabili, non puoi ignorarla per un’arena “morta”.
  • Catalyst dominates: se il catalyst e asset-specific, l’arena corretta e quella dell’asset; indice solo fallback.
  • EQUITIES_NEWS requires target: se primary_arena_today=EQUITIES_NEWS allora watchlist_target.length>=1, altrimenti arena DISABLED.
  • Universe consistency: primary_arena_today richiede universe_today[primary_arena_today].length>=1.
  • Instrument consistency: ogni setup candidato deve avere instruments ⊆ universe_today[arena], altrimenti SKIP.
  • Challenge rules override: i vincoli della challenge disabilitano intere arena.

Esempi

  • Crypto vola: ArenaScore(CRYPTO) alto, FOREX basso → primary_arena_today = CRYPTO (setup TREND/BREAKOUT).
  • News Tesla: Catalyst TSLA-specific → primary_arena_today = EQUITIES_NEWS (TSLA), indice solo fallback.

10.1 Definizione setup (standard auditabile)

  • Setup = regole operative + regime valido + risk budget compatibile.
  • Un setup non esiste se non rispetta costi e vincoli ChallengeSpec.
  • Ogni setup deve avere: regime target, strumenti ammessi, trigger, stop, sizing base.

10.2 Pipeline per arrivare a setup reali

  1. Definire ChallengeSpec per programma (vincoli duri).
  2. Definire Risk/Cost Layer (costi reali, slippage, spread proxy).
  3. Definire Regime/Context con metrica osservabile.
  4. Proporre 2-3 setup candidati per regime, non per asset.
  5. Validare in replay con DecisionState serializzato.
  6. Attivare in produzione solo se passano stress test e regole di rischio.

10.3 Output minimo per un setup reale

  • setup_id, name, regime_target, instruments
  • trigger_rules, invalidation_rules
  • risk_per_trade_pct, max_trades, cooldown
  • cost_assumptions, expected_edge_range
  • compliance_flags (news/weekend/EA)

10.4 Setup Registry v0.1 (MVP cross-arena)

MVP: 1 setup per arena. Versione forte: 1 setup per arena × regime.

Regime (tassonomia minima e osservabile)

  • TREND
  • RANGE
  • BREAKOUT
  • EXPANSION (volatility expansion / momentum burst)
  • EVENT (asset-specific catalyst)

Regime signals (minimi, per arena):

  • FUTURES: TREND = sopra/sotto VWAP + HH/HL o LL/LH (M15–H1). RANGE = oscillazione attorno value/VWAP + compressione. BREAKOUT = rottura range (opening/premarket) + retest.
  • FOREX: BREAKOUT = break del range di sessione (Asia/Londra) + conferma. RANGE = ritorni ripetuti verso mid-range con volatilita compressa. TREND = swing HH/HL o LL/LH su H1/H4.
  • CRYPTO: EXPANSION = compressione → break + retest con volatilita in aumento. RANGE = livelli ripetuti e assorbimento. TREND = struttura multi-TF + pullback su livello chiave.
  • EQUITIES_NEWS: EVENT = catalyst HIGH + livelli pre-news + comportamento post-news (continuation o reversal). Senza catalyst HIGH → arena DISABLED.

Arene (definizione minima)

  • FUTURES: ES/NQ; regimi tipici TREND/BREAKOUT; vincoli: news risk, orari sessione US.
  • FOREX: major FX; regimi tipici RANGE/BREAKOUT; vincoli: news macro, leverage, overnight.
  • CRYPTO: BTC/ETH perp; regimi tipici BREAKOUT/EXPANSION; vincoli: volatilita elevata, 24/7.
  • EQUITIES_NEWS: single-name (es. TSLA); regimi tipici EVENT; vincoli: catalyst required, orari.

Setup Pack v0.1 (1 per arena)

FUTURES — “VWAP Pullback Continuation”

  • arena: FUTURES
  • regime_target: TREND
  • instruments: ES, NQ
  • trigger_rules: trend sopra/sotto VWAP; pullback verso VWAP o zona di valore; candle di conferma
  • invalidation_rules: close decisivo oltre VWAP + struttura rotta
  • risk_per_trade_pct: da OperatingEnvelope
  • max_trades: 1–2 per sessione
  • cooldown: 10–20 min dopo loss
  • cost_assumptions: spread + slippage proxy (minimo)
  • compliance_flags: news filter ON, no-trade con event risk LIVE

Output: “Futures attivi → cerca pullback su VWAP.”

FOREX — “London Breakout / Session Range Break”

  • arena: FOREX
  • regime_target: BREAKOUT
  • instruments: EURUSD, GBPUSD, USDJPY
  • trigger_rules: break del range sessione Europa/Londra con conferma
  • invalidation_rules: rientro nel range + close opposto
  • max_trades: 1–2
  • cooldown: dopo falso breakout
  • compliance_flags: news filter ON

Output: “Forex attivo → breakout di sessione con conferma.”

CRYPTO — “Breakout + Retest su Volatility Expansion”

  • arena: CRYPTO
  • regime_target: BREAKOUT / EXPANSION
  • instruments: BTC, ETH
  • trigger_rules: compressione + break + retest con vol in espansione
  • invalidation_rules: rientro sotto livello + close opposto
  • max_trades: 1–2
  • cooldown: dopo falso breakout
  • compliance_flags: cost check aggressivo

Output: “Crypto in expansion → breakout + retest.”

EQUITIES_NEWS — “News Reversal / Continuation”

  • arena: EQUITIES_NEWS
  • regime_target: EVENT
  • instruments: single-name (es. TSLA)
  • trigger_rules: catalyst HIGH + livelli pre-news + impulso/assorbimento
  • invalidation_rules: perdita livello chiave + fallimento catalyst
  • requirements.catalyst_required: HIGH
  • max_trades: 1–2
  • cooldown: dopo failure news

Output: “Equities news attiva → catalyst-driven setup.”

Pipeline decisionale (8 righe)

  1. Trade Gate (OPEN/RESTRICTED/CLOSED)
  2. Risk Budget (risk per trade, max trades)
  3. Context (session + event risk + spread/liquidity proxy)
  4. Regime (TREND / RANGE / BREAKOUT / EXPANSION / EVENT)
  5. VenueSelection → primary_arena_today
  6. Setup candidates = SetupRegistry.filter(arena + regime + compliance + requirements)
  7. Cost check (se costi troppo alti → SKIP)
  8. Output: “Cerca questo setup su questo strumento”
  9. Se nulla passa → “No setup today”

13) Uncertainty & Cost Risk (obbligatorio)

  • Uncertainty aggregata: max(data_u, regime_u, execution_u, disagreement_u)
  • Haircut di rischio proporzionale all’incertezza
  • Cost model stocastico (expected + tail proxy)
  • Se cost tail > edge stimato → SKIP

Principi coerenti con evidenze su costi e turnover e con linee guida di risk management. [R1][R2][R3][R7]

13.1 Execution Kill-Switch

  • Spread anomalo o slippage fuori p99 → SKIP
  • 2 anomalie consecutive → HALT sessione

Kill-switch e controlli di rischio operativi sono raccomandati dalle best practice di mercato. [R10]

13.2 Soglie minime operative (v0.1, proxy-based)

  • Spread (ticks): RESTRICTED se spread > p95_hist, HALT se spread > p99_hist
  • Slippage (ticks): RESTRICTED se |slippage| > p95_hist, HALT se |slippage| > p99_hist o 2 anomalie consecutive
  • Volatilita locale (ATR 1m / range 1m): se > p95_hist → vieta setup RANGE, consenti TREND/ORB con sizing ridotto
  • TotalUncertainty: U = max(data_u, regime_u, execution_u, disagreement_u)
  • U ≥ 0.8 → SKIP; 0.5 ≤ U < 0.8 → DELAY/haircut; U < 0.5 → nominale

Le soglie sono derivate da distribuzioni empiriche (quantili robusti) su proxy osservabili e sostituite con dati di esecuzione reali quando disponibili.

13.3 Maturazione soglie (fasi)

  • Phase 0 (Proxy Calibration): soglie da quantili di proxy osservabili (spread stimato, range/ATR, volume).
  • Phase 1 (Paper/Sim log): execution logs sintetici (fill_time, slippage stimato, spread al trigger).
  • Phase 2 (Live/Contest): sostituzione con execution logs reali e recalibrazione.

14) Decision Policy Invariants & Testing

14.1 Invarianti hard

  1. Idempotenza: stesso state → stessa decisione
  2. Determinismo: nessuna randomness non controllata
  3. No bypass vincoli ChallengeSpec/RiskBudget
  4. Fail-safe: dati mancanti → SKIP
  5. Monotonicita: piu incertezza non rende piu permissivo

14.2 Test minimi (property-based)

  • test_idempotence(DecisionState)
  • test_monotonicity_uncertainty(DecisionState[])
  • test_no_constraint_bypass(DecisionState)
  • test_fail_safe(malformed DecisionState)

14.3 Replay deterministico

  • Ogni DecisionState serializzato deve poter essere rieseguito
  • Replay deve produrre stessa PolicyDecision
  • Policy/model version fissate per replay

14.4 Invarianti hard (vincoli contrattuali)

  • risk_budget.risk_per_trade_pct <= daily_loss_pct / max_trades
  • trade_gate = CLOSED se daily_loss_used_pct_today >= daily_loss_pct o max_dd_used_pct >= max_dd_pct
  • se news_trading_allowed = false e event_risk in {SCHEDULED,LIVE} ⇒ trade_gate != OPEN
  • se now non e in session_window.allowed_blocks ⇒ trade_gate = CLOSED (default fail-safe)
  • eccezione: se configurato after_hours_policy="RESTRICTED" e non in hard_cutoff ⇒ trade_gate = RESTRICTED
  • se event_risk = SCHEDULED e now nel buffer ⇒ trade_gate != OPEN (policy definita)
  • se event_risk = SCHEDULED e nel buffer ⇒ action = DELAY (default) e reason_codes include SESSION.FAIL.EVENT_BUFFER_ACTIVE
  • action=TRADE ⇒ trade_gate=OPEN e selected_setup_id != null
  • action in {SKIP,HALT} ⇒ selected_setup_id = null

14.5.2 Action ↔ Reason Matrix (vincoli contrattuali)

Regola generale: ogni PolicyDecision.action deve essere coerente con i reason_codes, altrimenti e invalid decision.

action reason_codes OBBLIGATORI (almeno 1) reason_codes VIETATI
TRADE TRADE.OK.ALL_GATES | TRADE.OK.WITH_HAIRCUT qualsiasi *.FAIL.*, EXEC.HALT.*, RISK.FAIL.*
DELAY REGIME.REVIEW.* | SESSION.FAIL.EVENT_BUFFER_ACTIVE | RISK.RESTRICT.PACING_SLOW EXEC.HALT.*, DATA.FAIL.*, CONSTRAINT.HARD.*
SKIP DATA.FAIL.* | CONSTRAINT.* | VENUE.FAIL.* | SETUP.FAIL.* | COST.FAIL.* TRADE.OK.*, EXEC.HALT.*
HALT EXEC.HALT.* TRADE.OK.*, SETUP.*, VENUE.*

Vincoli aggiuntivi

  • action=TRADE ⇒ selected_setup_id presente e instruments ⊆ universe_today[arena]
  • action∈{SKIP,HALT} ⇒ selected_setup_id = null
  • action=HALT ⇒ trade_gate = CLOSED
  • action=TRADE ⇒ trade_gate = OPEN
  • action=DELAY ⇒ trade_gate = RESTRICTED (non CLOSED)

14.6 DecisionState Canonical Serialization + Hash Spec (Determinismo)

14.6.1 Scopo

Garantire replay deterministico: stesso DecisionState ⇒ stesso hash ⇒ stessa PolicyDecision.

14.6.2 Canonicalization Rules (hard)

  • Campi in ordine fisso (schema canonico)
  • Numeri arrotondati: scores/uncertainty/confidence → 2 decimali; cost_distribution.expected/tail_risk → 4 decimali
  • Array ordinati: watchlist_target ASC; universe_today[arena] ASC
  • timestamp_utc_iso deve essere ISO-8601 UTC con suffisso Z (es. 2026-01-29T19:15:00Z)
  • signal_candidates_sorted ordinati per setup_id ASC e poi expected_edge DESC
  • Nessun campo opzionale omesso: se assente usare null (non missing)

14.6.3 Canonical Form (DecisionStateCanonical v1)

DecisionStateCanonical(v1) {
  timestamp_utc_iso,
  constraints: {
    trade_gate,
    hard_limits: { ... },
    risk_budget: { ... }
  },
  data_quality: { freshness, integrity, coverage },
  uncertainty: { data_u, regime_u, execution_u, disagreement_u },
  regime: { state, confidence, transition_risk },
  market: { volatility_level, liquidity_proxy, session, event_risk },
  path_state: { loss_streak, recovery_mode, pacing_status },
  cost_distribution: { expected, tail_risk },
  venue_selection: {
    venue_gate,
    primary_arena_today,
    secondary_arena,
    watchlist_target_sorted,
    fallback_index_sorted,
    catalyst_strength,
    universe_today_sorted
  },
  signal_candidates_sorted: [ { setup_id, expected_edge } ]
}

14.6.4 Hash Spec

state_hash = SHA256( JSON.stringify(DecisionStateCanonical(v1)) )

14.6.5 Replay Invariant (test)

  • same canonical JSON ⇒ same state_hash
  • same state_hash + same policy_version ⇒ same PolicyDecision

19) Conclusione

Il sistema e auditabile solo se regole statiche, risk layer e contesto sono separati e tracciati, con governance, testing e security formalizzati. Il motore deve essere dinamico rispetto a vincoli, mercato e volatilita. Il percorso verso setup reali richiede definizione rigorosa, test e cost model realistico prima del rilascio.
